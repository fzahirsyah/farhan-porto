Event Spotlight

Event management and ERP for Indonesian event organisers, with ticketing designed against scalpers (calo). This is a working prototype that runs entirely in your browser. No server, no installation.

Open every app in the same Chrome profile. They share one database stored in the browser, so a ticket bought in the shop shows up in the back office and at the gate. Keep the shared/ folder next to the app folders.

1. Start here

  1. Open erp/index.html. Choose Demo data (a concert, "Nusantara Sound Fest", is prepared). You can also start empty or open a .sqlite backup.
  2. Log in by tapping a person and typing their PIN (the PIN is printed on each card in the demo).

3. A 10-minute walkthrough

  1. Fair sales. ERP, Ticketing, Lottery: publish the seed fingerprint, run the draw, verify it. Then in the shop open #/lottery, check a result, and buy through a winner's link.
  2. Anti-calo wallet. Shop, My wallet: the QR changes every 30 seconds. Transfer a ticket (flat Rp5.000 fee paid by the seller, at most face value). The old ticket stops working.
  3. Gate. Crew app, Scan tab, Practice tools: a fresh code is admitted, an old (screenshot) code is refused, a second scan says already used. Switch to Work offline, scan, then go online to sync. Conflicts are shown and the earliest scan wins.
  4. Dispute desk. A guest whose ticket was already used is sent to the desk: a code goes to the real buyer's phone, then a rescue ticket comes from a reserved pool.
  5. Money. ERP, Vendors and orders: a vendor invoice that does not match the order or has no delivery confirmation cannot be paid without a written exception. Accounting shows the trial balance, income statement and balance sheet; they stay balanced after every action.
  6. Proposals. ERP, Proposals: write a sponsor proposal, send it, open the link in the partner portal, accept it. A quotation, contract and invoice are created.
  7. Control room. ERP, Control room, for the event-day wall display. Run the simulator in the crew app and watch it move.
  8. Configuration. ERP, Settings: every rule has layers (platform, organiser, project, event, ticket type). Changes are drafts, then published, logged and reversible. Sensitive changes after sales open need a second person.

4. Decisions built in

  • Ticket money goes 100% to the organiser except the payment admin fee. The software fee is one plan of Rp5.000.000 per organiser per year, no per-ticket fee.
  • Resale cap 100% of face value. Transfer fee flat Rp5.000, paid by the seller.
  • No approval limits by amount. A second person is needed only to export attendee data and to change ticket rules after sales open.
  • Sales order: community presale, public lottery, then open sale with a random queue.

5. Honest limits of this prototype

  • Data lives only in this browser (IndexedDB). Clearing site data deletes it. Use Settings, Database, Download backup often. Anyone with access to the browser profile can read the data.
  • Payments, SMS and email are simulated. Codes appear on screen and in the Outbox. Nothing leaves your computer.
  • Offline gate checking uses a shared secret per ticket stored on the phone. A real product should use public-key signatures so a stolen phone cannot forge tickets.
  • Camera QR scanning needs a browser with BarcodeDetector (Chrome on Android). Typing the code always works. Booth counting by camera is simple motion tracking; the simulator is for rehearsal. Real AI head-counting would need a proper model.
  • Tax rates (PPN, PPh 23, stamp duty) are placeholders and unverified. Have an accountant check them before use.
  • The service worker (offline shell for the crew app) only works when served over http(s) or localhost, not from a file.
  • Fonts load from Google Fonts when online and fall back to system fonts offline.
  • The demo has the "scan only on event day" rule switched off so you can rehearse today.
  • A prototype is not a security audit. Before real money: server-side checks, real payment gateway, legal and data-protection review (Indonesia PDP law).
